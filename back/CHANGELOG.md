## [v0.37.0] - 2026-10-25

### Added

- **OpenID Connect IdP surface (LBDS-303)**:
    - `app/Http/Controllers/OidcController.php` (new) — three endpoints: `discovery()` (OIDC Discovery 1.0 metadata, issuer pinned to `config('jwt.issuer')`, URLs derived from the request or the `OIDC_BASE_URL` config so path-rewriting proxies stay correct; the env value is validated — an unparseable value silently falls back to the request-derived base), `userinfo(Request, JwtService)` (Bearer access token, standard OIDC claim set filtered by granted scopes, rejects tokens without a `client_id` claim so SSO-web login tokens cannot be presented as IdP access tokens, applies per-client `claim_overrides` on top of the standard claim set, shared `reservedClaims()` list with the id_token so an override cannot make the two surfaces disagree), `endSession(Request, JwtService)` (validates `id_token_hint`, revokes every refresh token and session row for the user, validates `post_logout_redirect_uri` against the client's registered `redirect_url` as open-redirect protection, 302 with `state` echo on success, HTML confirmation page in degraded mode when no id_token_hint is provided — the copy explicitly says no logout happened so a phishing link cannot convince a user their session ended).
    - `app/Http/Controllers/OAuth2Controller.php` — `authorize` / `approveAuthorization` accept and validate the `scope` and `nonce` request fields; PKCE is required for public clients (no `client_secret`) and optional for confidential ones per RFC 7636 §1 (the original ticket's defense-in-depth ask was narrowed by the pre-merge review as an RFC deviation bigger than the threat model needs); controller-level checks reject half-formed PKCE (challenge without method) with a 400 + domain message.
    - `app/Http/Requests/AuthorizeRequest.php` — `code_challenge` and `code_challenge_method` are nullable at the FormRequest level; the conditional public-vs-confidential rule is enforced in the controller with full client context.
    - `app/Http/Requests/TokenRequest.php` — `code_verifier` is nullable; the "challenge present but verifier missing" check moves into `OAuth2Service::handleAuthorizationCode` where the auth code + client context is available.
    - `app/Models/OAuthAuthCode.php` — `scope` and `nonce` columns added.
    - `app/Models/SsoClient.php` — `allowed_scopes` JSON column (defaults to `openid profile email offline_access` for legacy clients via `effectiveAllowedScopes()`), `claim_overrides` JSON column (`effectiveClaimOverrides()` exposes it), `isPublic()` is the single source of truth for the public-vs-confidential PKCE rule.
    - `app/Models/UserRefreshToken.php` — `scope` + `client_id` columns added so refresh-token rotations preserve the OAuth2 scope and the originating client_id (otherwise `/oauth/userinfo` would silently drop profile/email claims and per-client `claim_overrides` after the first rotation).
    - `app/Services/AuthService.php` — `generateRefreshToken()` accepts `?string $scope` and `?string $clientId`; `refreshAccessToken()` reads them off the existing row and threads them into `generateTokenForJkt` / `generateToken`, so the rotated access token carries the same claims. Pre-migration refresh tokens (scope+client_id null) keep the old behaviour, so back-compat is preserved.
    - `app/Services/JwtService.php` — `buildToken()` accepts `?string $clientId` and emits a `client_id` claim when set; new `generateIdToken(User, SsoClient, ?nonce, scopes, ?authTime, extraClaims)` builds the OIDC id_token with `aud=client_id` (single-element list per RFC 7519), 10-minute lifetime via `jwt.id_token_expiration`, scope-driven claim inlining (`name`/`preferred_username`/`updated_at` for `profile`, `email`/`email_verified` for `email`, omitted for advanced ZKE users), and the per-client `extraClaims` applied on top. New `reservedClaims()` is the single source of truth for the OIDC REQUIRED + scope-derived claim list shared between id_token and userinfo, so a `claim_overrides` entry cannot make the two surfaces disagree.
    - `app/Services/OAuth2Service.php` — `createAuthorizationCode(User, SsoClient, data, ?scope, ?nonce)` persists scope + nonce; `resolveScope(SsoClient, ?rawScope)` defaults to the client's full allowed_scopes when the request omits scope, fails closed on unknown tokens; `handleAuthorizationCode` skips the PKCE verifier check for confidential clients with no challenge, issues the id_token when `openid` is in the granted scope, persists scope + client_id on the refresh token.
    - `config/jwt.php` — `id_token_expiration` (env `JWT_ID_TOKEN_EXPIRATION`, default 600s) and `oidc_base_url` (env `OIDC_BASE_URL`, optional) keys.
    - `database/migrations/2026_10_12_000000_add_scope_to_oauth_auth_codes_and_sso_clients.php` (new) — `scope` on `oauth_auth_codes`, `allowed_scopes` on `sso_clients`.
    - `database/migrations/2026_10_12_000001_add_nonce_to_oauth_auth_codes.php` (new) — `nonce` on `oauth_auth_codes`.
    - `database/migrations/2026_10_12_000002_add_claim_overrides_to_sso_clients.php` (new) — `claim_overrides` JSON on `sso_clients`.
    - `database/migrations/2026_10_12_000003_add_scope_and_client_id_to_user_refresh_tokens.php` (new) — `scope` + `client_id` on `user_refresh_tokens`.
    - `routes/api.php` — `GET /.well-known/openid-configuration`, `GET /oauth/userinfo` (under the `jwt.auth` group), `GET /oauth/logout`.
    - `docs/oidc-idp.md` (new, 450 lines) — integration guide for external RPs: discovery, registration, authorization code flow with PKCE, id_token verification, userinfo, refresh tokens, RP-initiated logout, per-client claim overrides, end-to-end copy-paste curl run, operational notes.
- **OIDC IdP test coverage (LBDS-303)**: 56 new tests across `OidcDiscoveryTest` (5), `OAuth2ScopeTest` (5), `OidcUserinfoTest` (9), `OidcIdTokenTest` (11), `OAuth2PkceEnforcementTest` (10), `OidcClaimOverridesTest` (7), `OidcEndSessionTest` (8), `OidcReservedClaimsTest` (3), `OAuth2RefreshTokenScopeTest` (3). Pin every claim shape, scope filter, reserved-claim guard, PKCE conditional, and refresh-token round-trip. Pre-merge review findings F1–F9 + F5.1 / F6.1 / F7.1 (13 findings) are covered by tests; F4.1 is the documented RFC 7636 vs. defense-in-depth trade-off.

## [0.2.0] - 2026-10-11

### Added

- **TOTP (RFC 6238) 2FA fallback (LBDS-8)**:
    - `app/Services/TotpService.php` (new) — RFC 6238 implementation: base32 codec, HOTP/TOTP, encrypted-at-rest secret (Laravel Crypt), ±1-step window per RFC §5.2, last-used-step anti-reuse, 10-code backup generation with re-roll on collision. Anti-reuse race closed via `lockForUpdate` (LBDS-8 review B-01). Backup codes use a Crockford-style alphabet (no I/O/0/1/l) to avoid hand-transcription errors.
    - `app/Models/TotpCredential.php`, `app/Models/TotpBackupCode.php` (new) — credentials and single-use codes scoped to the user.
    - `app/Models/User.php` — `totpCredential()`, `activeTotpCredential()` (whereNotNull confirmed_at), `totpBackupCodes()` relations.
    - `app/Models/UserActivityLog.php` — `ACTION_TOTP_ENROLLED`, `ACTION_TOTP_DISABLED`, `ACTION_TOTP_VERIFIED`, `ACTION_TOTP_BACKUP_CODE_REGENERATED` audit constants.
    - `app/Http/Controllers/AuthController.php` — `startTotpChallenge()` helper invoked from `login()` and `loginAdvancedVerify()` after the email-verified gate; on a hit the response is `{ code: 'TOTP_REQUIRED', totp_token, digits, period }` and a one-time cache entry holds the password-step state for 5 minutes. New endpoints: `totpEnrollStart` (regenerates a secret, returns the otpauth URI), `totpEnrollConfirm` (verifies the first code, emits 10 backup codes), `totpDisable` / `totpBackupCodesRegenerate` (require password for basic, derived `auth_proof` for advanced ZKE users — same re-auth contract as `passkeyDelete`), `totpStatus`, `totpLogin` (challenge step that consumes the cache entry, accepts `code` or `backup_code`).
    - `database/migrations/2026_10_08_000000_create_totp_credentials_table.php` (new) — credentials table, encrypted secret column, `last_used_step` anti-reuse counter.
    - `database/migrations/2026_10_08_000001_create_totp_backup_codes_table.php` (new) — backup codes table, `code_hash` Argon2id, `used_at` timestamp.
    - `database/migrations/2026_10_09_000000_add_composite_index_to_totp_backup_codes_table.php` (new) — composite `(user_id, used_at)` index on `totp_backup_codes` so the hot "is this code still valid?" query becomes an index range scan (LBDS-8 review B-08).
    - `routes/api.php` — 7 new TOTP routes; `/api/totp/login` tightened to `throttle:3,1` because the `totp_token` is an unauthenticated bearer, and the enrollment endpoints get `throttle:5,1` to stop an authenticated user spamming `start` to rotate their secret and wipe their backup codes (LBDS-8 review B-03 / B-10).
- **TOTP tests** (26): `tests/Unit/TotpServiceTest.php` covers the base32 round-trip and RFC 6238 Appendix B test vectors; `tests/Feature/TotpEnrollmentTest.php` covers every endpoint; `tests/Feature/TotpLoginTest.php` covers the login challenge path including a concurrency regression test for the anti-reuse race.
- **Passkey / Ed25519 (COSE alg -8) registration support (LBDS-257)**:
    - `app/Services/PasskeyService.php` — `generateRegistrationOptions()` now advertises `-8` (Ed25519) first in `pubKeyCredParams`, followed by ES256 (-7) and RS256 (-257). Authenticator preference order matches the WebAuthn spec; legacy authenticators still fall back to ES256 / RS256.
    - `app/Services/PasskeyService.php` (constructor) — the ceremony factory now receives an `AlgorithmManager` registered with `Cose\Algorithm\Signature\EdDSA\EdDSA` plus ES256/RS256, so the `CheckSignature` step accepts Ed25519 signatures at both attestation and assertion time. The default factory manager only ships ES256/RS256, so this wiring was required for Ed25519 to work end-to-end.
    - `app/Services/PasskeyService.php` (constructor) — the `AttestationStatementSupportManager` now includes `Webauthn\AttestationStatement\PackedAttestationStatementSupport` (the common `fmt="packed"` format used by YubiKey 5, Windows Hello and Android Passkeys). `NoneAttestationStatementSupport` is added automatically by the manager. The serializer (`WebauthnSerializerFactory`) is wired to the same manager so packed attestations deserialize on the way back in.
    - `tests/Feature/PasskeyMultiCredentialTest.php` — `test_registration_options_advertise_ed25519_algorithm` pins the advertisement contract; `test_ceremony_factory_algorithm_manager_includes_eddsa` and `test_ceremony_factory_attestation_manager_supports_packed_format` (Reflection) lock the internal wiring so a regression in the constructor fails the test surface; `test_registration_options_excludes_multiple_credentials_regardless_of_alg` and `test_authentication_options_accepts_multiple_allowed_credentials` cover the cross-alg exclude / allow paths. The existing 17 passkey tests stay green (21 passed, 52 assertions in the final run).
- **Documentation: hardening snapshot at `v0.35.0` (LBDS-249)**: new `docs/architecture/security.md` documents the security posture of the stack — authentication, transport hardening, token binding (DPoP), JWT hardening, rate limits, validation, observability — with explicit deferral decisions for LBDS-258 (DPoP ECDSA P-256), LBDS-257 (Ed25519 Passkeys), and LBDS-259 (mTLS, regulatory-only). Internal tracking at `odd/tasks/lbds-249-epic-close-decision.md`.
- **DPoP cutover is operator-driven via a config flag (LBDS-290)**: `config('jwt.dpop_allowed_algs')` defaults to `['ES256', 'RS256']` (the post-LBDS-258 dual-allowlist) and reads from the `DPOP_ALLOWED_ALGS` env var at runtime via `AppServiceProvider::bindDpopAllowedAlgs()`. Setting `DPOP_ALLOWED_ALGS=ES256` tightens the allowlist without a redeploy and survives `php artisan config:cache` (the env read happens on every request, so the cached config is overwritten at boot). The verifier rejects any `alg` outside the allowlist with the existing `"Algoritmo DPoP no soportado: <alg>"` message. A typo (e.g. `DPOP_ALLOWED_ALGS=HS256`) is sanitised at boot against the supported set and logged as a `Log::warning` so on-call sees the misconfiguration before traffic hits it. See `back/docs/DPOP_CUTOVER_RUNBOOK.md` for the two-stage cutover procedure.
- **DPoP proof-verified metric emitted per request (LBDS-290)**: `VerifyDpopProof` now logs a single structured line `event=dpop_proof_verified alg=<RS256|ES256> result=<accepted|rejected>` on every verification path. The line goes through the configured Laravel log channel with a triple-fallback chain (primary → `single` → `error_log`) so a broken log pipeline never silently drops the cutover counter. The captured `alg` is the real header value on every rejection path (allowlist miss, bad signature, thumbprint mismatch, missing claims, replay), so the runbook's `dpop_proofs_total{alg,result}` queries work end-to-end. The line is best-effort: a logging failure does NOT turn a valid proof into an invalid one (the verifier's contract is auth, not telemetry).

### Changed

- **DPoP allowlist env resolution moved out of the config file (LBDS-290 review)**: `back/config/jwt.php` no longer calls `env()` for the allowlist — the file ships a hard-coded default. `AppServiceProvider::bindDpopAllowedAlgs()` reads `DPOP_ALLOWED_ALGS` at request time and sanitises the value against the supported set (`['ES256','RS256']`). This closes the `config:cache` footgun flagged by the pre-merge review: a cached config no longer freezes the allowlist to whatever the env was at cache time, so tightening the cutover is now a one-line `.env` change without `config:clear` or a redeploy.

### Fixed

- **Passkey ceremony forwards stored transports incl. `hybrid` (LBDS-225)**:
    - `app/Services/PasskeyService.php` — new public `getAuthenticationDescriptors(User)` and `getRegistrationExcludeDescriptors(User)` pair each stored `transports` list with its credential id. New private `buildDescriptor(string|array)` accepts either the legacy string shape (back-compat for any external caller) or the new `['credential_id','transports']` shape; `normalizeTransports(array|null)` filters against `PublicKeyCredentialDescriptor::AUTHENTICATOR_TRANSPORTS`, dedupes, and returns `[]` when nothing valid is persisted (which `PublicKeyCredentialDescriptorNormalizer` then omits from JSON, letting the browser surface every authenticator). A guard rejects descriptor entries whose `credential_id` is missing / non-string / empty with `InvalidArgumentException` so a future caller wiring `buildDescriptor` directly cannot silently produce a `PublicKeyCredentialDescriptor` with `id=''`.
    - `app/Http/Controllers/AuthController.php` — `passkeyRegisterStart` and `passkeyAuthenticateStart` consume the new helpers instead of `getCredentialIds` / bare credential ids, so `excludeCredentials[]` and `allowCredentials[]` actually carry the stored transports to the browser.
    - `tests/Feature/PasskeyMultiCredentialTest.php` — 11 new tests (8 introduced in this ticket + 3 from the pre-merge review). Pins the contract end-to-end through both `/api/passkey/register/start` and `/api/passkey/authenticate/start`, exercises the legacy string input path, the `cable` and `smart-card` WebAuthn transports, the guard's failure modes (missing / null / non-string / empty `credential_id`) via a data provider, and a unit test for `normalizeTransports` in isolation via reflection (same pattern as the existing ceremony-factory tests in this file).
- **Packed attestation Ed25519 + `x5c` cert chains now verify (LBDS-286)**:
    - `app/Webauthn/PackedAttestationStatementSupportWithEdDSA.php` (new) — wrapper that registers under `fmt="packed"` in `AttestationStatementSupportManager` and intercepts only the `EdDSA + CertificateTrustPath` case (YubiKey 5 series, Windows Hello TPM, several Android devices). The upstream `PackedAttestationStatementSupport` is `final` and its `processWithCertificate()` throws on EdDSA because `openssl_verify` does not handle Ed25519; the wrapper extracts the leaf cert's Ed25519 public key via the pki-framework classes and verifies the signature with `sodium_crypto_sign_verify_detached`. Every other case (ES256/RS256 x5c, all self-attestations, all non-EdDSA) is forwarded to a wrapped upstream instance unchanged. The FIDO-format cert checks (Subject-O/OU/CN, non-CA, AAGUID extension) are re-implemented locally because the upstream `checkCertificate()` is `private`. Defense-in-depth: the SPKI algorithm OID is checked to be Ed25519 (`1.3.101.112`) before extraction, and library internals are redacted from the public exception message. The wrapper tracks the upstream fix path in its class docblock and should be removed once the lib release with the fix is pinned in `composer.json`.
    - `app/Services/PasskeyService.php` — wires the wrapper into the `AttestationStatementSupportManager` ahead of the upstream handler so it occupies the `fmt="packed"` slot. Closes the "Known limitation (tracked as LBDS-286)" note from the LBDS-257 entry above.
    - `tests/Unit/PackedAttestationStatementSupportWithEdDSATest.php` (new) — 8 unit tests covering: happy path with a self-signed Ed25519 cert (real FIDO-format Subject + AAGUID extension, signed with libsodium), invalid signature rejected, non-Ed25519 SPKI rejected, library error redaction, non-EdDSA + x5c delegation, EdDSA + `EmptyTrustPath` (self-attestation) delegation, AAGUID match / mismatch paths. Test fixtures (cert PEM, raw public key, libsodium secret key) are baked in as constants so the suite is hermetic — no `exec('openssl ...')` calls.
    - `tests/Feature/PasskeyMultiCredentialTest.php` — `test_ceremony_factory_attestation_manager_supports_packed_format` updated: the slot is now occupied by the wrapper, not the raw upstream class; the assertion checks the wrapper class and the `AttestationStatementSupport` contract.
- **Logout `refresh_token` clear cookie now mirrors emission attributes (LBDS-278)**:
    - `app/Http/Controllers/AuthController.php` — `logout()` previously called `Cookie::forget('refresh_token', '/', null, true, true)`, whose `Secure` and `SameSite` flags were independent of `config('session.secure')` / `config('session.same_site')` (Laravel's `CookieJar::forget` falls back to defaults cached at framework boot, while the emission helper `refreshTokenCookie()` reads the config at call time). The clear is now built through a new private `refreshTokenForgetCookie()` helper that mirrors `refreshTokenCookie()` attribute-for-attribute, so emission and clear agree on `Secure`, `SameSite`, `HttpOnly` and `Path` even when `SESSION_SECURE_COOKIE=false` in dev. Browsers match cookies by name+path+domain, so the clear worked correctly before — this is defense-in-depth and removes the F4 finding surfaced by the LBDS-252 review.
    - `tests/Feature/RefreshTokenCookieAttributesTest.php` — 4 new regression tests pin emission/clear attribute parity both at the helper level (reflection-based) and end-to-end through a real login + logout round-trip, including the runtime `config(['session.secure' => false])` override scenario the previous implementation failed.
- **DPoP allowlist-reject no longer double-counted in the cutover metric (LBDS-290 re-review)**: `VerifyDpopProof::validateDpopProof()` sets a dedupe flag after emitting the `alg_not_in_allowlist` metric, so the outer catch in `verify()` / `verifyTokenRequest()` does not emit a second `verification_failed` line for the same request. The previous behaviour double-counted every allowlist-rejected proof in `dpop_proofs_total{result="rejected"}`, inflating the dashboard by 2x during the cutover observation window.

### Security

- **TOTP secret encrypted at rest (LBDS-8)**: secrets are stored via `Crypt::encryptString` (AES-256-CBC via APP_KEY). A DB leak does not expose usable secrets. Operational risk: APP_KEY rotation requires re-encrypting the column.

## [0.1.0] - 2026-09-27

> **Note:** v0.1.0 is the first versioned release of `back/CHANGELOG.md`. v0.1.0 corresponds to the v0.35.0 monorepo tag (2026-09-27). `back/composer.json` is a Laravel project and does not carry a `version` field; the monorepo git tag is the source of truth. Entries below were in `[Unreleased]` at the tag point. The CHANGELOG lag is closed retroactively here.

### Added

- **CORS rejection diagnostics (LBDS-261)**: `HandleDynamicCors` now stamps every rejected origin with `X-CORS-Rejected: origin-not-allowed`, plus `X-CORS-Origin`, `X-CORS-Client` and `X-CORS-Allowed`, so a missing origin is visible in devtools instead of surfacing as a generic browser CORS error. A rejected preflight (`OPTIONS`) answers `204` with those headers instead of falling through to a `405`, and it still omits `Access-Control-Allow-Origin` so the browser keeps blocking it. The allowlist header is only emitted when the request names a resolvable `client_id`, so the union of every active client's origins is never published.
- `App\Support\OriginNormalizer`: canonical `scheme://host[:port]` comparison shared by the CORS middleware and the OAuth redirect validation (returns `null` for non-http schemes such as native app callbacks).
- `App\Support\CorsOrigins`: single source of truth for the origins the CORS layer honours for a client, cache included, consumed by both the middleware and the OAuth redirect validation so the two cannot disagree.
- `database/migrations/2026_09_19_000000_add_dpop_jkt_to_user_refresh_tokens_table.php` (new) — nullable indexed `dpop_jkt` column on `user_refresh_tokens`; the binding is inherited by every rotated token.
- `app/Services/JwtService.php` — `generateTokenForJkt()` issues a `cnf.jkt`-bound access token from a stored thumbprint; `generateToken()` keeps emitting exactly the same claims as before, so existing login flows are untouched.
- `app/Services/AuthService.php` — `jktFromDpopPublicKey()` derives the RFC 7638 thumbprint from the raw `dpop_public_key` field. Only the authorization-code exchange binds its refresh token: the login/cookie flow has no DPoP proof mechanism on refresh, so binding there would lock those sessions out.
- `tests/Feature/DpopRefreshTokenTest.php` (new) and `tests/Support/DpopProofBuilder.php` — 18 integration tests over the real endpoints, covering every enforced failure (missing header, wrong key, tampered signature, wrong `htm`/`htu`, stale `iat`, replayed `jti`, `ath` without a bearer, unbound token, revoked-token replay) and the success path with binding preservation and rotation.

### Changed

- **OAuth redirect validation (LBDS-261)**: `POST /api/oauth/authorize` and `POST /api/oauth/authorize/approve` now reject with `400` a `redirect_uri` whose origin is not covered by the client's effective CORS origins, before issuing an authorization code. Previously the code was issued, the browser was redirected, and the token exchange then died silently in CORS, leaving the user logged into the SSO but not into the app. The check only applies to public clients: a client holding a secret may exchange the code server-to-server, where CORS never applies.
- **`redirect_url` is required for `authorization_code` clients**: the OAuth endpoints return `400` for a client without a configured `redirect_url` (previously any redirect URI was accepted), and the admin create/update requests now require it when `grant_types` includes `authorization_code`, so a client can no longer be saved into a state that always fails at authorize.
- `app/Services/AuthService.php` — the rotated access token keeps the DPoP binding (`cnf.jkt`) instead of degrading to a Bearer token, and the DPoP enforcement runs after the token-state checks so that replaying a revoked token still revokes the whole chain.
- `app/Http/Middleware/VerifyDpopProof.php` — token-endpoint proofs are verified by `verifyTokenRequest()`, sharing the bound-token validation path with an optional `ath` claim (validated against the presented bearer when present).

### Fixed

- **`Allowed origins` field validation no longer swallowed by the app-config copy**: the frontend catalog entry for the origin mismatch requires both `allowed_origins` and `redirect_uri` to match, so an `allowed_origins`-only field-validation error keeps its own message.
- `app/Http/Middleware/VerifyDpopProof.php` — `jwkToPem()` fed a raw `n||e` blob to `openssl_pkey_get_public()` and built an extra ASN.1 `SEQUENCE`, so every DPoP signature verification failed; the correct SubjectPublicKeyInfo structure is now produced.
- `app/Http/Middleware/VerifyDpopProof.php` — the replay check called `DB::getPdo()->rowCount()`, which does not exist on `PDO` and aborted every verification; the `INSERT IGNORE` now runs through `DB::affectingStatement()`.
- `app/Http/Requests/TokenRequest.php` — a structurally invalid `dpop_public_key` (not RSA or missing `kty`/`n`/`e`) is rejected with 422 instead of raising an uncaught `InvalidArgumentException`.

### Security

- The CORS rejection diagnostic no longer discloses the union of every active client's allowed origins when no `client_id` can be resolved from the request.
- `app/Services/AuthService.php` — the OAuth `refresh_token` grant (`POST /api/oauth/token`) requires a DPoP proof whose JWK thumbprint matches the binding stored on the refresh token; a refresh token without a binding is rejected with 401, which forces existing OAuth sessions created before this change to log in again once.
- `app/Services/AuthService.php` — a refresh token that carries a DPoP binding can only be rotated with a valid matching proof on every refresh endpoint (`/api/oauth/token` and `/api/refresh-token`), so a stolen bound token can no longer be redeemed through the cookie-only endpoint to obtain an unbound access token.
- **Session and refresh_token cookies now ship with hardened defaults (LBDS-252)**: the `SameSite=Lax` / `Secure=null` defaults in `config/session.php` were permissive; they are now `SameSite=Strict` / `Secure=true` so the cookie jar that defends login sessions against CSRF and cross-site theft no longer relies on each operator remembering to flip two env vars in production. The flags are still env-overridable for local HTTP dev. `config/session.php` now also treats blank/non-value env strings (`SESSION_SAME_SITE=` or `=null`) as the safe default rather than letting them fall through to a Symfony `null` SameSite that silently regresses the hardening.
    - `app/Http/Controllers/AuthController.php`: a single private `refreshTokenCookie()` helper now centralizes the four `refresh_token` emission sites (basic login, advanced login, passkey login, `/api/refresh-token` rotation) so they cannot diverge. The regression test pins every emission site through the helper, since the helper is the contract.
    - `config/sanctum.php`: docblock warns that registering `Laravel\Sanctum\Http\Middleware\EnsureFrontendRequestsAreStateful` would silently reset `session.same_site` to `Lax` at runtime — do not add it to the middleware groups.
    - `back/.env.production.example`: `SESSION_SAME_SITE` template updated from `lax` → `strict` (the template already shipped with `SESSION_SECURE_COOKIE=true`).
    - `tests/Feature/RefreshTokenCookieAttributesTest.php` (new): six regression tests pin the hardened attributes (SameSite=Strict, HttpOnly, Secure from config, path `/`), the helper, and the IIFE policy on `session.same_site` / `session.secure` defaults.
- **Throttle coverage for `/oauth/token` (LBDS-251)**:

- **`/oauth/token` sliding-window rate limit (LBDS-251)**: see the matching `### Added` entry above for the design. The dedicated middleware imposes per-`(client_id, IP)` and per-IP buckets on the token endpoint; the two buckets run in parallel and the more restrictive wins, mitigating brute force on `refresh_token` / `client_credentials` grants against a known client and enumeration of valid `client_id` values from a fixed source. `grant_type=authorization_code` is intentionally excluded because PKCE + the auth-code's short TTL + single-use already cover that flow; the legacy upstream `throttle:10,1` remains in place as a generic IP cap.
- **Canonical UUID v4 `jti` claim on every issued JWT (LBDS-254)**: `app/Services/JwtService.php` — `buildToken` (also reached by `generateToken` and `generateTokenForJkt`), `generateClientToken`, and `issueProfileToken` now mint the `jti` claim via `Str::uuid()->toString()` instead of `bin2hex(random_bytes(16))`. `Str::uuid()` uses the same `random_bytes()` CSPRNG; UUID v4 reserves 4 bits for the version field and 2 for the variant (RFC 4122), so per-token entropy is 122 bits (still ≫ any cryptographic threshold). The change is lexical so logs, audit tooling, and a future RFC 7009 revocation endpoint can treat `jti` as a parseable UUID v4 identifier. Every emission — including refresh-token rotation through `generateTokenForJkt` — mints a fresh `jti`, so two consecutive access tokens for the same user always carry distinct identifiers and the predecessor can be revoked independently. `tests/Unit/JwtServiceJtiTest.php` (new, 8 tests) pins the format and uniqueness across every builder; `tests/Feature/JwtJtiClaimTest.php` (new, 6 tests) exercises the live HTTP endpoints (`/api/login`, `/api/oauth/token` authorization_code + refresh_token, `/api/refresh-token`) decoding each emitted JWT end-to-end. Persistence of the `jti ↔ session` mapping and the `/oauth/revoke` endpoint itself are out of scope here and tracked as a follow-up.
- **`kid` header on every issued JWT + kid-aware verification (LBDS-256)**: `app/Services/JwtService.php` now stamps the configured `kid` (`config('jwt.kid')`, env `JWT_KID`, default `sso-key-1`) into the protected header of every JWT — `buildToken`, `generateClientToken`, and `issueProfileToken` — via `withHeader('kid', ...)` before signing. `app/Services/AuthService.php` — `getJwks()` derives its `keys` array from `config('jwt.keys')` instead of a hardcoded `sso-key-1`, so rotating the signing key is a config-only change. `back/config/jwt.php` exposes a `kid` entry plus a forward-compatible `keys` list (default ships a single entry mirroring `kid`). `parseAndValidateToken` is now kid-aware: it parses first, reads `headers().kid`, resolves to the matching key when present, and falls back to the primary key when the header is absent (preserves back-compat for tokens issued before this release); an unknown `kid` returns `null` rather than silently using the wrong key. `packages/sso-server/src/Jwt/JwksFetcher.php` exposes `getPublicKeyPemByKid(string $kid)` with a per-kid cache and a new `JwksFetchException::unknownKid()` factory; `packages/sso-server/src/Jwt/JwtValidator.php` — `validate()` parses first, resolves PEM by `kid` with primary-key fallback for absent `kid`. `tests/Unit/JwtServiceKidTest.php` (new, 5 tests + 3 parse-path tests) pins the header on every builder and the kid-aware parse contract; `tests/Feature/JwksKidTest.php` (new, 2 tests) cross-checks the JWKS endpoint and a live login token header. `packages/sso-server/tests/Unit/JwksFetcherKidTest.php` (new, 5 tests) and `tests/Unit/JwtValidatorKidTest.php` (new, 2 tests) cover the package-side resolution and fallback.
