## [Unreleased]

### Added

- **Passkey / Ed25519 (COSE alg -8) registration support (LBDS-257)**:
    - `app/Services/PasskeyService.php` — `generateRegistrationOptions()` now advertises `-8` (Ed25519) first in `pubKeyCredParams`, followed by ES256 (-7) and RS256 (-257). Authenticator preference order matches the WebAuthn spec; legacy authenticators still fall back to ES256 / RS256.
    - `app/Services/PasskeyService.php` (constructor) — the ceremony factory now receives an `AlgorithmManager` registered with `Cose\Algorithm\Signature\EdDSA\EdDSA` plus ES256/RS256, so the `CheckSignature` step accepts Ed25519 signatures at both attestation and assertion time. The default factory manager only ships ES256/RS256, so this wiring was required for Ed25519 to work end-to-end.
    - `app/Services/PasskeyService.php` (constructor) — the `AttestationStatementSupportManager` now includes `Webauthn\AttestationStatement\PackedAttestationStatementSupport` (the common `fmt="packed"` format used by YubiKey 5, Windows Hello and Android Passkeys). `NoneAttestationStatementSupport` is added automatically by the manager. The serializer (`WebauthnSerializerFactory`) is wired to the same manager so packed attestations deserialize on the way back in.
    - `tests/Feature/PasskeyMultiCredentialTest.php` — `test_registration_options_advertise_ed25519_algorithm` pins the advertisement contract; `test_ceremony_factory_algorithm_manager_includes_eddsa` and `test_ceremony_factory_attestation_manager_supports_packed_format` (Reflection) lock the internal wiring so a regression in the constructor fails the test surface; `test_registration_options_excludes_multiple_credentials_regardless_of_alg` and `test_authentication_options_accepts_multiple_allowed_credentials` cover the cross-alg exclude / allow paths. The existing 17 passkey tests stay green (21 passed, 52 assertions in the final run).
    - **Known limitation (tracked as LBDS-286)** — packed attestation with `x5c` certificate chains still fails at server-side signature verification because the upstream `web-auth/cose-lib` `COSE_ALGORITHM_MAP` lacks EdDSA. Self-attestation credentials register and assert cleanly; affected authenticators (YubiKey 5, Windows Hello with TPM) fall back to ES256 / RS256 via the browser's algorithm selection until LBDS-286 lands.
- **CORS rejection diagnostics (LBDS-261)**: `HandleDynamicCors` now stamps every rejected origin with `X-CORS-Rejected: origin-not-allowed`, plus `X-CORS-Origin`, `X-CORS-Client` and `X-CORS-Allowed`, so a missing origin is visible in devtools instead of surfacing as a generic browser CORS error. A rejected preflight (`OPTIONS`) answers `204` with those headers instead of falling through to a `405`, and it still omits `Access-Control-Allow-Origin` so the browser keeps blocking it. The allowlist header is only emitted when the request names a resolvable `client_id`, so the union of every active client's origins is never published.
- `App\Support\OriginNormalizer`: canonical `scheme://host[:port]` comparison shared by the CORS middleware and the OAuth redirect validation (returns `null` for non-http schemes such as native app callbacks).
- `App\Support\CorsOrigins`: single source of truth for the origins the CORS layer honours for a client, cache included, consumed by both the middleware and the OAuth redirect validation so the two cannot disagree.
- `database/migrations/2026_09_19_000000_add_dpop_jkt_to_user_refresh_tokens_table.php` (new) — nullable indexed `dpop_jkt` column on `user_refresh_tokens`; the binding is inherited by every rotated token.
- `app/Services/JwtService.php` — `generateTokenForJkt()` issues a `cnf.jkt`-bound access token from a stored thumbprint; `generateToken()` keeps emitting exactly the same claims as before, so existing login flows are untouched.
- `app/Services/AuthService.php` — `jktFromDpopPublicKey()` derives the RFC 7638 thumbprint from the raw `dpop_public_key` field. Only the authorization-code exchange binds its refresh token: the login/cookie flow has no DPoP proof mechanism on refresh, so binding there would lock those sessions out.
- `tests/Feature/DpopRefreshTokenTest.php` (new) and `tests/Support/DpopProofBuilder.php` — 18 integration tests over the real endpoints, covering every enforced failure (missing header, wrong key, tampered signature, wrong `htm`/`htu`, stale `iat`, replayed `jti`, `ath` without a bearer, unbound token, revoked-token replay) and the success path with binding preservation and rotation.
- **Documentation: hardening snapshot at `v0.35.0` (LBDS-249)**: new `docs/architecture/security.md` documents the security posture of the stack — authentication, transport hardening, token binding (DPoP), JWT hardening, rate limits, validation, observability — with explicit deferral decisions for LBDS-258 (DPoP ECDSA P-256), LBDS-257 (Ed25519 Passkeys), and LBDS-259 (mTLS, regulatory-only). Internal tracking at `odd/tasks/lbds-249-epic-close-decision.md`.

### Changed

- **OAuth redirect validation (LBDS-261)**: `POST /api/oauth/authorize` and `POST /api/oauth/authorize/approve` now reject with `400` a `redirect_uri` whose origin is not covered by the client's effective CORS origins, before issuing an authorization code. Previously the code was issued, the browser was redirected, and the token exchange then died silently in CORS, leaving the user logged into the SSO but not into the app. The check only applies to public clients: a client holding a secret may exchange the code server-to-server, where CORS never applies.
- **`redirect_url` is required for `authorization_code` clients**: the OAuth endpoints return `400` for a client without a configured `redirect_url` (previously any redirect URI was accepted), and the admin create/update requests now require it when `grant_types` includes `authorization_code`, so a client can no longer be saved into a state that always fails at authorize.
- `app/Services/AuthService.php` — the rotated access token keeps the DPoP binding (`cnf.jkt`) instead of degrading to a Bearer token, and the DPoP enforcement runs after the token-state checks so that replaying a revoked token still revokes the whole chain.
- `app/Http/Middleware/VerifyDpopProof.php` — token-endpoint proofs are verified by `verifyTokenRequest()`, sharing the bound-token validation path with an optional `ath` claim (validated against the presented bearer when present).

### Fixed

- **Logout `refresh_token` clear cookie now mirrors emission attributes (LBDS-278)**:
    - `app/Http/Controllers/AuthController.php` — `logout()` previously called `Cookie::forget('refresh_token', '/', null, true, true)`, whose `Secure` and `SameSite` flags were independent of `config('session.secure')` / `config('session.same_site')` (Laravel's `CookieJar::forget` falls back to defaults cached at framework boot, while the emission helper `refreshTokenCookie()` reads the config at call time). The clear is now built through a new private `refreshTokenForgetCookie()` helper that mirrors `refreshTokenCookie()` attribute-for-attribute, so emission and clear agree on `Secure`, `SameSite`, `HttpOnly` and `Path` even when `SESSION_SECURE_COOKIE=false` in dev. Browsers match cookies by name+path+domain, so the clear worked correctly before — this is defense-in-depth and removes the F4 finding surfaced by the LBDS-252 review.
    - `tests/Feature/RefreshTokenCookieAttributesTest.php` — 4 new regression tests pin emission/clear attribute parity both at the helper level (reflection-based) and end-to-end through a real login + logout round-trip, including the runtime `config(['session.secure' => false])` override scenario the previous implementation failed.
- **`Allowed origins` field validation no longer swallowed by the app-config copy**: the frontend catalog entry for the origin mismatch requires both `allowed_origins` and `redirect_uri` to match, so an `allowed_origins`-only field-validation error keeps its own message.
- `app/Http/Middleware/VerifyDpopProof.php` — `jwkToPem()` fed a raw `n||e` blob to `openssl_pkey_get_public()` and built an extra ASN.1 `SEQUENCE`, so every DPoP signature verification failed; the correct SubjectPublicKeyInfo structure is now produced.
- `app/Http/Middleware/VerifyDpopProof.php` — the replay check called `DB::getPdo()->rowCount()`, which does not exist on `PDO` and aborted every verification; the `INSERT IGNORE` now runs through `DB::affectingStatement()`.
- `app/Http/Requests/TokenRequest.php` — a structurally invalid `dpop_public_key` (not RSA or missing `kty`/`n`/`e`) is rejected with 422 instead of raising an uncaught `InvalidArgumentException`.

### Security

- The CORS rejection diagnostic no longer discloses the union of every active client's allowed origins when no `client_id` can be resolved from the request.
- `app/Services/AuthService.php` — the OAuth `refresh_token` grant (`POST /api/oauth/token`) requires a DPoP proof whose JWK thumbprint matches the binding stored on the refresh token; a refresh token without a binding is rejected with 401, which forces existing OAuth sessions created before this change to log in again once.
- `app/Services/AuthService.php` — a refresh token that carries a DPoP binding can only be rotated with a valid matching proof on every refresh endpoint (`/api/oauth/token` and `/api/refresh-token`), so a stolen bound token can no longer be redeemed through the cookie-only endpoint to obtain an unbound access token.
- **Session and refresh_token cookies now ship with hardened defaults (LBDS-252)**: the `SameSite=Lax` / `Secure=null` defaults in `config/session.php` were permissive; they are now `SameSite=Strict` / `Secure=true` so the cookie jar that defends login sessions against CSRF and cross-site theft no longer relies on each operator remembering to flip two env vars in production. The flags are still env-overridable for local HTTP dev. `config/session.php` now also treats blank/non-value env strings (`SESSION_SAME_SITE=` or `=null`) as the safe default rather than letting them fall through to a Symfony `null` SameSite that silently regresses the hardening.
    - `app/Http/Controllers/AuthController.php`: a single private `refreshTokenCookie()` helper now centralizes the four `refresh_token` emission sites (basic login, advanced login, passkey login, `/api/refresh-token` rotation) so they cannot diverge. The regression test pins every emission site through the helper, since the helper is the contract.
    - `config/sanctum.php`: docblock warns that registering `Laravel\Sanctum\Http\Middleware\EnsureFrontendRequestsAreStateful` would silently reset `session.same_site` to `Lax` at runtime — do not add it to the middleware groups.
    - `back/.env.production.example`: `SESSION_SAME_SITE` template updated from `lax` → `strict` (the template already shipped with `SESSION_SECURE_COOKIE=true`).
    - `tests/Feature/RefreshTokenCookieAttributesTest.php` (new): six regression tests pin the hardened attributes (SameSite=Strict, HttpOnly, Secure from config, path `/`), the helper, and the IIFE policy on `session.same_site` / `session.secure` defaults.
- **Throttle coverage for `/oauth/token` (LBDS-251)**:
  - `tests/Feature/ThrottleTokenEndpointTest.php` (new, 9 tests) — integration coverage through the real route (`authorization_code` bypass, 11th refresh request returns `429` with `Retry-After`, headers on success, IP isolation, shared IP bucket across two client_ids, invalid client_id anti-enumeration, burst limit at 21st request, `CACHE_STORE=file` graceful degradation, rolling-window weight with `Carbon::setTestNow`).
  - `tests/Unit/ThrottleTokenEndpointMiddlewareTest.php` (new, 8 tests) — direct unit coverage that bypasses the HTTP routing layer so the middleware's bucket logic is exercised even if the upstream `throttle:10,1` ever changes (proves the dedicated throttle is the effective gate, not the generic one).
  - `routes/api.php` — `/oauth/token` now carries `['throttle:10,1', 'throttle.token']` (the dedicated middleware runs on top of the existing generic throttle for defense in depth).
  - `bootstrap/app.php` — alias `throttle.token` registered for `App\Http\Middleware\ThrottleTokenEndpoint`.
- **`/oauth/token` sliding-window rate limit (LBDS-251)**: see the matching `### Added` entry above for the design. The dedicated middleware imposes per-`(client_id, IP)` and per-IP buckets on the token endpoint; the two buckets run in parallel and the more restrictive wins, mitigating brute force on `refresh_token` / `client_credentials` grants against a known client and enumeration of valid `client_id` values from a fixed source. `grant_type=authorization_code` is intentionally excluded because PKCE + the auth-code's short TTL + single-use already cover that flow; the legacy upstream `throttle:10,1` remains in place as a generic IP cap.
- **Canonical UUID v4 `jti` claim on every issued JWT (LBDS-254)**: `app/Services/JwtService.php` — `buildToken` (also reached by `generateToken` and `generateTokenForJkt`), `generateClientToken`, and `issueProfileToken` now mint the `jti` claim via `Str::uuid()->toString()` instead of `bin2hex(random_bytes(16))`. `Str::uuid()` uses the same `random_bytes()` CSPRNG; UUID v4 reserves 4 bits for the version field and 2 for the variant (RFC 4122), so per-token entropy is 122 bits (still ≫ any cryptographic threshold). The change is lexical so logs, audit tooling, and a future RFC 7009 revocation endpoint can treat `jti` as a parseable UUID v4 identifier. Every emission — including refresh-token rotation through `generateTokenForJkt` — mints a fresh `jti`, so two consecutive access tokens for the same user always carry distinct identifiers and the predecessor can be revoked independently. `tests/Unit/JwtServiceJtiTest.php` (new, 8 tests) pins the format and uniqueness across every builder; `tests/Feature/JwtJtiClaimTest.php` (new, 6 tests) exercises the live HTTP endpoints (`/api/login`, `/api/oauth/token` authorization_code + refresh_token, `/api/refresh-token`) decoding each emitted JWT end-to-end. Persistence of the `jti ↔ session` mapping and the `/oauth/revoke` endpoint itself are out of scope here and tracked as a follow-up.
- **`kid` header on every issued JWT + kid-aware verification (LBDS-256)**: `app/Services/JwtService.php` now stamps the configured `kid` (`config('jwt.kid')`, env `JWT_KID`, default `sso-key-1`) into the protected header of every JWT — `buildToken`, `generateClientToken`, and `issueProfileToken` — via `withHeader('kid', ...)` before signing. `app/Services/AuthService.php` — `getJwks()` derives its `keys` array from `config('jwt.keys')` instead of a hardcoded `sso-key-1`, so rotating the signing key is a config-only change. `back/config/jwt.php` exposes a `kid` entry plus a forward-compatible `keys` list (default ships a single entry mirroring `kid`). `parseAndValidateToken` is now kid-aware: it parses first, reads `headers().kid`, resolves to the matching key when present, and falls back to the primary key when the header is absent (preserves back-compat for tokens issued before this release); an unknown `kid` returns `null` rather than silently using the wrong key. `packages/sso-server/src/Jwt/JwksFetcher.php` exposes `getPublicKeyPemByKid(string $kid)` with a per-kid cache and a new `JwksFetchException::unknownKid()` factory; `packages/sso-server/src/Jwt/JwtValidator.php` — `validate()` parses first, resolves PEM by `kid` with primary-key fallback for absent `kid`. `tests/Unit/JwtServiceKidTest.php` (new, 5 tests + 3 parse-path tests) pins the header on every builder and the kid-aware parse contract; `tests/Feature/JwksKidTest.php` (new, 2 tests) cross-checks the JWKS endpoint and a live login token header. `packages/sso-server/tests/Unit/JwksFetcherKidTest.php` (new, 5 tests) and `tests/Unit/JwtValidatorKidTest.php` (new, 2 tests) cover the package-side resolution and fallback. Rotation procedure documented in `docs/AUTHENTICATION.md` § 7 — Key Rotation.
